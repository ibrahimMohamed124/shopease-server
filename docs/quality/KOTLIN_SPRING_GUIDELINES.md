# Kotlin-Specific Rules for Spring Boot

These rules apply to all Kotlin code in ShopEase. They are based on the official Kotlin, Spring Framework, and Spring Boot documentation linked at the end. Confirm version-specific details against the documentation matching the versions actually pinned in this repository; do not blindly copy examples from a different Spring Boot/Kotlin release.

## 1. Check the build before changing Kotlin configuration

- Inspect `build.gradle.kts`, the Gradle wrapper, the Spring Boot plugin version, Kotlin plugin versions, the JDK toolchain, and dependency management first.
- Keep Kotlin compiler plugins and Kotlin libraries aligned to a compatible Kotlin version. Prefer the versions managed/recommended by the selected Spring Boot release; do not independently upgrade Kotlin, Hibernate, Spring, Jackson, or compiler plugins as part of an unrelated feature.
- Verify that `kotlin-stdlib` and `kotlin-reflect` are on the runtime classpath. A project generated by Spring Initializr may already provide them; do not add duplicates without checking.
- Verify `com.fasterxml.jackson.module:jackson-module-kotlin` is present when Jackson serializes/deserializes Kotlin classes. Confirm it is actually registered by the project's configured JSON mapper.
- Use the project’s existing Gradle Kotlin DSL conventions. Do not migrate build tools or rewrite the build file without a concrete task requirement.
- Prefer compiler/build configuration recommended for the exact Kotlin version in use. For Kotlin 2.2+ check the official guidance concerning annotation default targets (including `-Xannotation-default-target=param-property`) and adopt it consistently when appropriate. Do not add compiler flags without checking compatibility and warnings.

## 2. Kotlin compiler plugins: Spring and JPA are not interchangeable

- Verify that the `kotlin("plugin.spring")` / `org.jetbrains.kotlin.plugin.spring` plugin is correctly applied at a compatible version. Kotlin classes are final by default, while Spring commonly needs proxyable classes/methods for features such as declarative transactions, method security, caching, and AOP.
- Verify that the JPA no-arg support plugin (`kotlin("plugin.jpa")` / `org.jetbrains.kotlin.plugin.jpa`) is configured when using JPA entities that require synthetic no-argument constructors.
- **Do not assume the JPA plugin automatically makes entities open.** It supplies JPA-oriented no-arg support; check the actual entity openness strategy against Hibernate proxy/lazy-loading requirements. If subclass proxies are required, configure openness for `@Entity`, `@Embeddable`, and `@MappedSuperclass` deliberately, or use a documented compatible strategy such as suitable bytecode enhancement. Do not apply a broad all-open rule without understanding which types it opens.
- Confirm all Kotlin Gradle plugin versions are aligned. Do not paste plugin snippets with hard-coded versions from unrelated documentation into this project.
- Do not casually remove the Spring/JPA compiler plugins to “fix” a compilation issue. First identify which runtime behavior the plugin enables.

## 3. Null-safety and Java interoperability

- Model nullability honestly: use `T` for required values and `T?` only when absence is a valid part of the contract.
- Avoid `!!`. If a value can be absent, handle that case explicitly (`?:`, a domain-specific exception, or a nullable return) and preserve intended HTTP behavior.
- Treat Java platform types and values from Java libraries as potentially nullable unless annotations/contracts prove otherwise. Add tests at interoperability boundaries.
- Do not use `lateinit` as a shortcut for dependency injection or normal application state. Prefer constructor injection and explicit initialization.
- Avoid leaking nullable persistence details into public API responses unintentionally. Verify missing-versus-null behavior for request DTOs and JSON serialization.
- Do not change Kotlin/Jackson null/default behavior without API contract tests. A constructor default may cause an omitted JSON field to behave differently from an explicitly provided `null`.

## 4. Annotation use-site targets and validation

Kotlin properties can generate constructor parameters, fields, getters, and setters. A Java annotation may need an explicit use-site target.

- For Bean Validation on DTO properties, use the target required by the configured compiler and validation provider, commonly `@field:NotBlank`, `@field:Email`, `@field:Size`, and similar annotations.
- Do not mechanically delete `@field:` / `@get:` / `@param:` annotations because they look verbose.
- When adopting Kotlin 2.2+ annotation-default-target settings, inspect how existing framework annotations are emitted and verify runtime validation and binding with tests.
- Keep request-shape validation at the API boundary and business invariants in the appropriate domain/application layer.
- Use explicit validation groups or custom validators only when there is a real requirement; avoid building a validation framework for simple DTOs.

Example:

```kotlin
data class RegisterRequest(
    @field:NotBlank
    @field:Email
    val email: String,

    @field:NotBlank
    @field:Size(min = 8, max = 72)
    val password: String
)
```

Use the actual project's password policy and field limits; the values above are illustrative, not a product decision.

## 5. Data classes, JPA entities, and domain types

- Prefer `data class` for request/response DTOs, commands, query results, and other immutable value carriers where generated `equals`, `hashCode`, `copy`, and `toString` are appropriate.
- Do not automatically use `data class` for JPA entities. Generated equality/copy/string methods can interact badly with entity identity, mutable IDs, lazy associations, bidirectional relationships, and proxies.
- For JPA entities, explicitly consider identity semantics, no-arg construction, open/proxy requirements, ID generation, mutability, and lazy-loading behavior. Do not make every association `EAGER` to avoid proxy concerns.
- Keep JPA entities out of controller responses and cross-module contracts. Map to API DTOs or projections deliberately.
- Use `enum class` for stable, finite states where appropriate, but verify database and JSON representation before changing existing enum storage/serialization.
- Use `BigDecimal` for money; define currency, scale, and rounding from actual business requirements.
- Use value classes (`@JvmInline value class`) for domain identifiers/value types only when interoperability with JPA, Jackson, Spring Data, serialization, and Java APIs is understood and tested. They are not a default wrapper for every ID.
- Do not use `copy()` on mutable persistence entities as a substitute for domain state transitions.

## 6. Spring proxies, transactions, and AOP

- Use constructor injection; avoid field injection and service locator patterns.
- Put `@Transactional` on a meaningful application/use-case boundary, based on required atomicity.
- Understand proxy-based behavior: self-invocation of a method on the same object may bypass the Spring proxy, so an internal method call should not be assumed to trigger `@Transactional`, `@Cacheable`, `@Async`, or other proxy-based advice.
- Ensure classes/methods can be proxied as required by the configured Kotlin plugins and Spring proxy mode.
- Do not assume a transaction makes database updates race-free, nor that it can roll back a remote HTTP/payment/email operation.
- Do not switch a whole application to coroutines, reactive programming, or WebFlux because Kotlin supports them. Use Spring MVC for conventional request/response APIs unless a measurable requirement justifies a different model.
- If using `suspend` functions or reactive types, verify end-to-end support for the exact Spring Data, transaction, security, and client libraries in use; do not mix blocking JPA calls into reactive request paths expecting non-blocking behavior.

## 7. Kotlin coding conventions

- Prefer immutable `val` by default; use `var` only where mutation is required by the design or framework.
- Prefer small, explicit functions and meaningful domain names over clever one-liners, nested scope functions, or overuse of extension functions.
- Avoid deeply chained `let`/`also`/`apply`/`run` blocks when ordinary statements are clearer.
- Do not use `runCatching` to swallow failures or accidentally convert infrastructure exceptions into success values. Handle expected errors explicitly and preserve transaction rollback semantics.
- Avoid generic `Map<String, Any?>` for stable request/response contracts; use typed DTOs. Use maps for genuinely dynamic data only.
- Avoid `GlobalScope`, unmanaged threads, and ad-hoc executors. Use Spring-managed scheduling/execution facilities when needed.
- Avoid blocking I/O in custom coroutine/reactive paths and avoid introducing coroutines where no concurrency benefit exists.
- Use `java.time` types with explicit timezone semantics. Do not assume a local timestamp is UTC.
- Keep exception types meaningful and translate them consistently at the API boundary; do not expose internal exception messages.

## 8. Kotlin-specific testing checklist

When a feature uses these facilities, test them rather than relying only on compilation:
- Jackson serialization/deserialization for nullable properties, constructor defaults, enums, dates, decimals, and Kotlin DTOs;
- Bean Validation on the actual constructor parameter/field/getter target used at runtime;
- JPA entity creation, persistence, generated IDs, and lazy-loading/proxy behavior;
- transaction rollback and Spring proxy behavior for annotated use cases;
- Kotlin-Java nullability and platform-type boundaries;
- pagination/projections without entity graph over-fetching.
